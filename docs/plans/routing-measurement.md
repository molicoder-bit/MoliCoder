# Routing measurement status

The offline comparison API in `local_model_chat.inference.routing_report` replays two policies against the same held-out scenarios. The baseline ranks currently eligible and authorized offerings by quoted token price, assuming every call succeeds. The tuned policy uses measured acceptance, retries, and latency from separate training scenarios. Both call the production router, so current privacy, capability, health, account, terms, price freshness, and authorization checks still apply.

Each observation names a scenario and offering and records acceptance, elapsed seconds, cost when known, retry count, intervention count, and failure. An evaluation scenario must contain an observed outcome for each policy's selected offering. Missing observations stop the comparison. The report includes accepted-task cost only when every selected cost is known and at least one task is accepted. It never treats an unknown cost as free.

`recorded_task_outcomes` now reads verified Build task completions alongside task-attributed local inference usage. It excludes tasks with opaque calls, multiple offerings, incomplete usage, or no timed start. A task with any unknown request cost has unknown task cost. Retry counts come from the task attempt record, and intervention counts come from review/takeover events. Existing requests without a task ID cannot be attributed retroactively.

This is a comparison mechanism, **not a measured improvement claim**. The comparison tests use constructed outcomes. Opaque CLI subscriptions still do not expose reliable per-task spend, and there are no matched real evaluation outcomes for competing offerings. A real routing change needs independent training and evaluation runs covering the same scenarios and each offering being compared. At least five observations per offering are required by the router before it uses measured metrics. Keep the production route policy unchanged until the measured report is reviewable.
